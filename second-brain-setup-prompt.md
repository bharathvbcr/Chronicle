# Prompt for Claude Code — Second Brain Vault Setup (skill-based architecture)

> **Chronicle users:** This prompt is inspiration for a generic Obsidian vault. For the live Chronicle product, follow [`chronicle-pc/CONTRACT.md`](chronicle-pc/CONTRACT.md) and seed structure with `chronicle init-vault-structure` (idempotent, create-only).

Copy everything below this line and paste it into Claude Code, run from an empty folder where you want the vault to live.

---

I want you to build a complete "Second Brain" knowledge vault in this directory. It will be operated entirely through Claude Code sessions and must also open cleanly as an Obsidian vault. This session has three phases: (1) build the full folder structure, a thin root CLAUDE.md router, and a set of project skills that contain the actual workflows; (2) interview me to seed the vault with my basic information and reshape the structure around my life; (3) teach me how to use it with a printed usage guide. Details below.

## 1\. Core concept and architecture

This vault is my second brain. Every message I type in a future session falls into one or more intents:

1. **CAPTURE** — I'm giving new information to store (facts, notes, ideas, meetings, decisions, contacts, documents, images).  
2. **RETRIEVE** — I'm asking a question answerable from vault contents.  
3. **MAINTAIN** — housekeeping: merge duplicates, fix links, archive, reorganize, rebuild indexes.

**The architecture is skill-based.** Intent routing is NOT implemented as logic in CLAUDE.md — it happens through Claude Code's automatic skill invocation. Each workflow lives in a hidden, auto-invoked project skill under `.claude/skills/`, and the skill `description` fields are written so that semantic matching against my message selects the right workflow. CLAUDE.md stays thin (it loads every session); skill bodies stay on disk until triggered. Procedural detail inside each skill is further split into supporting reference files that load only when needed (progressive disclosure).

A single message can carry mixed intent ("Sarah moved to Portland — do I have anything else on her?"). In that case invoke BOTH skills in one turn: capture first, then retrieve.

If intent is ambiguous, make the best guess, state the assumption in one line, and proceed. Never ask "do you want me to save this or search for it?" for obvious cases.

## 3\. Root CLAUDE.md — thin router

Keep this file SHORT (aim well under 100 lines). It must contain only:

**Vault map** — one line per top-level folder saying what belongs there.

**Intent routing** — a brief statement: "Workflows are defined in project skills. Capturing information → capture-workflow skill. Answering questions from the vault → retrieval-format skill. Housekeeping → vault-maintenance skill. Mixed-intent messages may invoke multiple skills in one turn (capture before retrieve). If a message states a preference about answer style, edit `_system/preferences.md` (this is a capture)."

**Hard rules that apply to every operation, regardless of skill:**

- Always use the real current date (run `date` when uncertain — never guess or assume the date). Resolve relative dates in my messages to absolute YYYY-MM-DD.  
- Never delete content; obsolete material moves to `90-Archive/` preserving its subpath.  
- Obsidian compatibility: plain markdown, `[[wikilinks]]` for internal links, `![[file.ext]]` for embeds, YAML frontmatter on every note, file names are note titles (Title Case, unique across the vault).  
- Never store passwords, API keys, or full account numbers; store a pointer like "see password manager".  
- Log every structural change (move/rename/merge/split/archive) as one line in `_system/changelog.md`.  
- Read `_system/conventions.md` before modifying files; nested CLAUDE.md files override the root for their subtree.  
- Be concise in chat; the durable output is the vault.

Nothing procedural beyond this — no capture steps, no retrieval steps. Those live in the skills.

## 4\. Skill 1: capture-workflow (hidden, auto-invoked)

`.claude/skills/capture-workflow/SKILL.md`

**Frontmatter:** `user-invocable: false`. Do NOT set `disable-model-invocation`.

**Description (write it for reliable triggering, contrastive with retrieval):** something like — "Use whenever the user provides information to store: declarative statements of fact, 'note that', 'remember this', 'save this', 'add to', pasted content, dropped files/images/PDFs, meeting summaries, or corrections to stored info ('actually it's X not Y'). Covers filing, note creation/editing, linking, reorganization, and attachments. Do NOT use for questions about existing information — that is retrieval-format."

**SKILL.md body — a tight checklist, not an essay:**

1. Classify the content type (fact, project update, person, meeting, journal entry, document, idea, preference, task/deadline).  
2. Preference about answer style? → edit `_system/preferences.md`, confirm in one line, done.  
3. Search the vault FIRST for an existing home (grep title keywords \+ synonyms, check `_system/index.md` and the relevant MOC). Prefer appending/updating over creating.  
4. If creating: pick destination folder (read its CLAUDE.md), use the matching `_templates/` template, fill frontmatter per `_system/conventions.md`.  
5. **Stamp real dates everywhere.** Use the actual current date (run `date` if unsure — never guess) for `created`/`updated` frontmatter and for any dated content. Resolve relative dates I use ("next Friday", "in two weeks", "last month") into absolute YYYY-MM-DD dates in the note, keeping my phrasing if useful ("follow up next Friday (2026-07-17)").  
6. **Anything with a due/expiry/follow-up date is a task, not just a fact.** Record it in the relevant note as an Obsidian checkbox with a date: `- [ ] Renew passport 📅 2027-03-01`. Also add a matching line to `Upcoming.md` under the right month, linking back to the source note. When I say something is done, check the box in the source note and remove it from Upcoming.md.  
7. **Person/entity notes get an `aliases` frontmatter list** — every name variant, nickname, email, or handle they might be referenced by (e.g., `aliases: [Sarah, Sarah Chen, sarah@acme.com]`). Add new aliases as they appear in later captures.  
8. Weave links: add `[[wikilinks]]` to every related existing note; add backlinks in those notes where natural; update the area MOC; update Home.md only if a new major area appeared.  
9. **Update `_system/index.md`**: add a line for every new note (title | type | tags | updated date); update the line on renames/moves.  
10. Attachment involved? → follow `attachments.md` in this skill folder.  
11. Note grew past \~300 lines, duplicates found, or content is misfiled? → follow `reorganization.md`.  
12. Unclear where it belongs? → file in `00-Inbox/` with a one-line "needs filing" marker.  
13. Confirm to the user in 1–2 lines: what was stored, where, what was linked.

**Supporting file `attachments.md`:** copy binary into `_attachments/` named `YYYY-MM-DD-description.ext`; create/update a companion note in the right folder that embeds the file (`![[...]]`), summarizes its contents as searchable text (read the PDF / describe the image), and lists the path under an `attachments:` frontmatter key.

**Supporting file `reorganization.md`:** criteria and procedures for splitting oversized notes into linked sub-notes, merging duplicates, moving misfiled notes, and archiving; the mandatory link-refactor rule — on any move/rename, grep the entire vault for wikilinks and markdown links to the old name/path and update every reference; changelog logging format.

## 5\. Skill 2: retrieval-format (hidden, auto-invoked)

`.claude/skills/retrieval-format/SKILL.md`

**Frontmatter:** `user-invocable: false`. Do NOT set `disable-model-invocation`.

**Description (contrastive with capture):** something like — "Use whenever the user asks a question about stored information: 'what did I say about', 'when did', 'find my notes on', 'remind me', 'do I have anything on', 'summarize what I know about', or any question answerable from vault contents. Governs both the search protocol and the answer format. Do NOT use for statements providing new information — that is capture-workflow."

**SKILL.md body:**

1. **First step, every time: read `_system/preferences.md`** and apply it to the response format.  
2. **Shortlist via the index before opening files.** Scan `_system/index.md` (title | type | tags | updated) to pick candidate notes, then grep in waves across all `.md` files — including `90-Archive/` — for keywords AND synonyms; check frontmatter tags and `aliases` (a person may be referenced by nickname or email); follow wikilinks up to two hops from hits. Only open the files that survive the shortlist — don't read the whole vault.  
3. **Handle temporal queries explicitly.** Get today's real date first (run `date` — never assume). For "last month", "recently", "this week", "what's coming up": filter using `created`/`updated` frontmatter, journal note dates, and dated lines inside notes. For "what's coming up / due" questions, read `Upcoming.md` first, then verify against source notes.  
4. **Recency wins conflicts.** When notes disagree, prefer the most recently updated one — but say that an older note conflicts and link both.  
5. **Flag staleness.** If the answer rests on a note not updated in over a year, say so: "this may be stale — last updated 2025-06-10."  
6. Lead with the direct answer, formatted per preferences. End with a "Sources:" line of wikilinks.  
7. Never fabricate vault contents — say plainly when nothing is found. If notes contradict each other, surface the contradiction instead of silently picking one.

## 6\. Skill 3: vault-maintenance (auto \+ manual)

`.claude/skills/vault-maintenance/SKILL.md`

**Frontmatter:** default invocation (I can run `/vault-maintenance`, and Claude may invoke it when I ask for housekeeping). Destructive bulk operations inside the skill must always list the planned changes and get my confirmation before executing.

**Description:** "Use when the user asks for vault housekeeping: weekly review, process the inbox, find duplicates or orphan notes, fix broken links, archive stale notes, audit frontmatter/naming, or rebuild MOCs."

**SKILL.md body:** inbox filing procedure (classify → move → link → update MOC → remove from inbox); **bulk import** — if `_staging/` contains files (exports from Apple Notes, docs, old vaults, spreadsheets, etc.), process them in batches through the capture-workflow rules: split multi-topic files into proper notes, file each into the right folder with frontmatter, links, aliases, and index entries, move any binaries to `_attachments/` with companion notes, and move processed originals to `90-Archive/_staging-originals/` so nothing is lost and `_staging/` ends empty; **regenerate `Upcoming.md`** — scan the vault for unchecked `- [ ]` items with 📅 dates, group by month, link each to its source note, flag overdue items at top, drop completed ones; **rebuild `_system/index.md`** from scratch by walking all notes (title | type | tags | updated), fixing any drift; orphan-note detection (no incoming or outgoing links); stale-note flagging (not updated in 90+ days → propose archiving); duplicate detection; frontmatter and naming audit against conventions.md; MOC rebuild. Broken-link repair details go in `link-repair.md`.

The description field should also name the import triggers: "import my notes", "process the staging folder", "migrate my old notes", plus "what's overdue", "update the upcoming list".

## 7\. \_system files and templates

**conventions.md** — single source of truth:

- Frontmatter schema required on every note:  
    
  \---  
    
  created: YYYY-MM-DD  
    
  updated: YYYY-MM-DD  
    
  type: note | project | person | meeting | journal | reference | attachment-note  
    
  tags: \[\]  
    
  aliases: \[\] (person/entity notes: all name variants, nicknames, emails, handles)  
    
  status: (projects only)  
    
  attachments: \[\] (only if any)  
    
  \---  
    
  `updated` must be bumped on every edit. All dates are real calendar dates — resolve relative phrasing to absolute YYYY-MM-DD at capture time.  
    
- Task format: `- [ ] description 📅 YYYY-MM-DD` for anything with a due/expiry/follow-up date; tasks live in their topical note AND get a linked line in `Upcoming.md`.  
- Naming: notes in Title Case; journal and meeting notes date-prefixed; attachments date-prefixed kebab-case.  
- Tagging: small controlled vocabulary, lowercase, hyphenated; prefer links over tags; list a starter tag set.  
- Linking: minimum one wikilink per note; MOCs link down, notes link laterally.

**preferences.md** — my answer-style preferences, structured so individual rules are easy to edit. Starting defaults:

- Default style: short summary first (2–4 sentences), details only if asked.  
- Bullets only when listing 3+ discrete facts; otherwise prose.  
- Verbosity triggers: go detailed when the question says "everything", "in detail", "full history", or similar.  
- Always end with wikilinked sources.  
- Per-topic overrides: an initially-empty section where topic-specific preferences accumulate (e.g., "finance questions: always include dates and amounts").

**changelog.md** — header row explaining the one-line-per-change format.

**index.md** — the retrieval shortlist: one line per note in the format `title | type | tags | updated`. Initialize it with all seed notes; capture keeps it current; maintenance rebuilds it from scratch.

**Upcoming.md** (vault root) — the rolling deadlines view: sections per month, each line an unchecked task with its 📅 date and a wikilink to the source note, overdue items flagged at top. Initialize empty with the section structure and a one-line explanation.

**\_staging/** — add a short README explaining: "Drop exports here (Apple Notes, docs, old vault files). Then ask Claude to 'import my staging folder' — files get processed into proper notes and originals are archived."

**\_templates/** — create `note.md`, `project.md`, `person.md`, `meeting.md`, `daily.md`, `attachment-note.md`, each with frontmatter and section stubs.

## 10\. Onboarding interview (run AFTER the structure is built)

Once every folder, file, and skill from sections 2–9 exists, switch modes and interview me. This is the only part of the whole setup where you SHOULD ask me questions.

**How to run it:**

- Ask in small batches (2–4 questions at a time), conversationally, not as one giant form. Wait for my answers before the next batch.  
- Every answer is a capture: file it into the vault following the capture-workflow rules (real notes, proper frontmatter, wikilinks, MOC updates) — not a single dump file.  
- I can skip any question or say "done" to end the interview early. Skipped topics are simply left out.

**Cover at minimum:**

1. **Identity basics** — name, what I do, where I'm based. → a "Me" note at the vault root or in `20-Personal/`, linked from Home.md.  
2. **Work landscape** — my job/business, active projects, key people I work with, tools/companies I deal with regularly. → seed notes in `10-Work/Projects/` and `10-Work/People/`.  
3. **Personal landscape** — family members and important people, health topics I track, financial areas I want organized, home/vehicle basics. → seed notes in `20-Personal/` subfolders.  
4. **Interests and knowledge areas** — topics I read about, hobbies, things I want to build knowledge on. → stub notes in `30-Knowledge/` linked to the Knowledge MOC.  
5. **Habits and preferences** — how I like answers formatted (update `_system/preferences.md` with anything I say), whether I plan to journal daily, anything I explicitly do NOT want stored.

**After the interview:** review what was created and reorganize if needed — if my answers revealed that the default folder structure doesn't fit my life (e.g., I have two businesses, or no use for a Travel folder), rename/add/remove folders accordingly, update the affected CLAUDE.md files and MOCs, fix all links, and log the changes in the changelog. The structure should end up shaped around MY life, not the template.

## 11\. Usage guide (print this at the very end)

After the interview and reorganization, print a short "How to use your Second Brain" guide directly in the chat, AND save it as `How To Use This Vault.md` at the vault root (linked from Home.md) so I can reread it in Obsidian. It must explain, with concrete examples:

**Adding information — just state it.** No command needed; declarative statements route to capture automatically:

- "Sarah from Acme is now my main contact for the Q3 project, her email is [sarah@acme.com](mailto:sarah@acme.com)"  
- "Note that my car insurance renews March 15, policy \#ABC123"  
- "Here's the contract PDF from the vendor" (with a dropped file)  
- "Actually, the meeting got moved to Thursday" (corrections update existing notes)

**Retrieving — just ask.** Questions route to retrieval automatically:

- "What do I know about Sarah from Acme?"  
- "When does my car insurance renew?"  
- "Summarize everything about the Q3 project"  
- "Do I have anything on vendor contracts from last year?"  
- Time-based questions work too: "What did I decide last month?" / "What's coming up in the next two weeks?" / "What's overdue?"

**Deadlines and follow-ups — state them like anything else.** Anything with a date becomes a tracked task automatically:

- "My passport expires March 2027" → checkbox task in the passport note \+ a line in \[\[Upcoming\]\]  
- "Follow up with Wade next week" → resolved to a real date and tracked  
- "I renewed the passport" → the task gets checked off and leaves Upcoming

**Importing existing notes — use the staging folder.** Export from Apple Notes, Google Docs, old vaults, etc., drop the files into `_staging/`, then say "import my staging folder". Files are split into proper notes, filed, linked, and the originals archived. Do this in batches if you have a lot.

**Capturing from your phone.** Sync this folder (iCloud, Obsidian Sync, or git) and open it in Obsidian mobile. Jot quick notes into `00-Inbox/` from anywhere — no special format needed. Next time you're in Claude Code, say "clean up my inbox" and everything gets filed properly.

**Changing how answers look — just say so.** These edit preferences and stick permanently:

- "Keep answers shorter" / "Always use bullet points" / "For finance questions, always include dates and amounts"

**Maintenance — ask or run the command:**

- "Clean up my inbox" / "Do a weekly review" / "Find broken links" — or type `/vault-maintenance`

**Tips section:** mixed messages work (store \+ ask in one sentence); when unsure where something went, ask "where did you file that?"; open the folder in Obsidian anytime — the graph view shows how notes connect; nothing is ever deleted, only archived.
